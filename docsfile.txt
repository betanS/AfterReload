1. INTRODUCCION

AfterReload es una aplicacion web orientada a la gestion de partidas privadas y competitivas de Counter-Strike dentro de una comunidad cerrada. La idea general del sistema es centralizar en una unica plataforma tareas que habitualmente se resuelven de forma dispersa o manual: autenticacion de usuarios, acceso a servidores, organizacion de lobbies, consulta del ranking, gestion de perfiles y administracion de usuarios.

El universo del discurso del proyecto se situa en el ambito de las plataformas web de soporte a comunidades de juego. No obstante, el valor principal del desarrollo no reside en el servidor de Counter-Strike como tal, sino en la construccion de un sistema de informacion web capaz de gestionar usuarios, datos, flujos de negocio, interfaces y comunicaciones con servicios externos. Por tanto, el nucleo evaluable del proyecto es la aplicacion web desarrollada con Laravel.

La funcionalidad principal del sistema consiste en permitir que un usuario autenticado acceda a la plataforma, consulte los servidores disponibles, entre en un lobby, participe en el flujo previo a una partida y disponga de informacion persistida como ranking, perfil o creditos. Junto a esta funcionalidad principal, la aplicacion incorpora un panel de administracion y una API JSON para integraciones externas.

Como ampliacion funcional, el sistema dispone de integraciones con elementos del ecosistema de juego, como Steam OpenID, webhooks de resultados y comandos RCON. Estas integraciones deben entenderse como complementarias: aportan automatizacion y realismo al producto, pero no son imprescindibles para comprender ni valorar la arquitectura, la logica de negocio ni la persistencia de la parte web.

Este documento incluye una introduccion general al sistema, los objetivos perseguidos, el estado del arte, la planificacion del desarrollo, la metodologia empleada, el lenguaje de modelado, los recursos utilizados y la arquitectura general de la solucion.

2. OBJETIVOS

2.1 Objetivo general

Disenar y desarrollar una aplicacion web que permita gestionar de forma centralizada el flujo de acceso y organizacion de partidas dentro de una comunidad privada, cubriendo desde la autenticacion del usuario hasta la consulta y actualizacion de informacion persistente.

2.2 Objetivos especificos

- Implementar una aplicacion web basada en arquitectura MVC con separacion clara entre modelos, vistas y controladores.
- Gestionar la autenticacion de usuarios de forma sencilla y coherente con el contexto de uso de la plataforma.
- Desarrollar un modulo de servidores y lobbies que permita consultar disponibilidad, entrar en sala, seleccionar equipo y actualizar estados.
- Disenar una base de datos relacional para usuarios, servidores, lobbies, configuraciones de partida y resultados.
- Construir un panel de administracion para roles, bloqueos y supervision basica de usuarios.
- Implementar una vista de ranking y un perfil de usuario con informacion persistida.
- Incorporar una tienda con filtrado, busqueda y paginacion sobre un catalogo local.
- Exponer una API JSON para permitir la comunicacion con servicios externos de forma desacoplada.
- Mantener la solucion enfocada en la parte web, de forma que pueda ser evaluada por si misma aunque las integraciones del servidor de juego no esten activas.

2.3 Necesidad cubierta

La necesidad principal que cubre el sistema es disponer de una plataforma web propia para organizar y administrar partidas privadas sin depender completamente de herramientas de terceros. En lugar de repartir la gestion entre aplicaciones distintas, la solucion concentra identidad, acceso, organizacion y control en una unica interfaz.

Desde el punto de vista del sistema de informacion, la aplicacion cubre tres necesidades concretas:
- centralizar la gestion de usuarios y permisos;
- organizar el flujo previo a la partida mediante lobbies y estados;
- persistir y mostrar informacion relevante para la comunidad, como ranking, perfil y administracion.

3. ESTADO DEL ARTE

3.1 Sistemas de informacion actuales

En el mercado existen plataformas y servicios que cubren parcialmente necesidades similares. Entre los referentes mas conocidos se encuentran FACEIT y ESEA, orientados al emparejamiento competitivo y a la gestion de partidas online. Tambien existen herramientas complementarias para servidores de Counter-Strike, como plugins de competicion, sistemas de estadisticas y servicios de autenticacion externa.

Sin embargo, estas soluciones suelen responder a escenarios distintos:
- plataformas masivas orientadas a ecosistemas cerrados;
- herramientas tecnicas centradas en el servidor de juego y no en la experiencia web global;
- servicios con poca capacidad de personalizacion para comunidades privadas pequenas o medianas.

En el contexto actual del desarrollo web, la tendencia general es construir aplicaciones ligeras pero conectadas, donde la capa web centraliza usuarios, interfaces, persistencia y comunicacion con APIs externas. Tambien es habitual combinar renderizado en servidor con JavaScript para enriquecer zonas concretas de la interfaz sin necesidad de una SPA completa.

3.2 Discusion

El trabajo desarrollado aporta una solucion adaptada a un escenario muy concreto: una comunidad privada que necesita una aplicacion web propia para gestionar sus partidas y sus usuarios. La principal aportacion no es competir con plataformas masivas, sino ofrecer una base web personalizable, mantenible y coherente con un entorno reducido y controlado.

Las diferencias principales respecto a otras soluciones son:
- el foco esta puesto en el sistema web y no exclusivamente en el servidor del juego;
- la logica funcional esta adaptada a una comunidad privada y no a un servicio generalista;
- la arquitectura permite desacoplar la aplicacion web de las integraciones externas;
- la solucion combina gestion de usuarios, ranking, lobby, administracion y tienda en una unica plataforma.

En consecuencia, el proyecto aporta valor por integracion y por adecuacion al problema, no por replicar a gran escala servicios ya existentes. Su interes tecnico reside en el desarrollo completo de una aplicacion web con persistencia, roles, interfaces, endpoints y capacidad de evolucion.

4. PLANIFICACION

4.1 Desarrollo del sistema de informacion

El desarrollo se ha planteado de manera incremental. En lugar de construir todo el sistema de una sola vez, se ha seguido una secuencia de ampliaciones progresivas sobre una base funcional minima. Esto ha permitido validar cada bloque del sistema antes de incorporar el siguiente.

La evolucion general del trabajo ha seguido este orden:
1. Definicion inicial del problema y del alcance de la plataforma web.
2. Modelado de entidades, relaciones y flujos principales.
3. Implementacion de autenticacion, estructura base y persistencia.
4. Desarrollo de vistas y navegacion principal.
5. Construccion de la logica de lobby, ranking y administracion.
6. Incorporacion de la API JSON y de integraciones externas.
7. Ajustes de usabilidad, roles, restricciones y documentacion.

4.2 Metodologia de desarrollo

La metodologia empleada es un desarrollo evolutivo basado en construccion de prototipos. Cada iteracion ha permitido disponer de una version funcional del sistema, validar decisiones tecnicas y refinar el producto a partir de nuevas necesidades detectadas durante la implementacion.

Las fases principales seguidas han sido:
- analisis: identificacion de requisitos, actores, entidades y casos de uso;
- diseno: definicion del modelo de datos, estructura de la aplicacion e interfaces;
- implementacion: desarrollo del backend, vistas, rutas, controladores y servicios;
- validacion: comprobacion de flujos funcionales y correccion de errores;
- pruebas: verificacion manual de acceso, navegacion, lobby, administracion, ranking y endpoints.

Esta metodologia resulta adecuada porque el proyecto combina varias capas funcionales y ha requerido ajustar detalles del flujo de usuario a medida que el sistema iba tomando forma.

4.3 Lenguaje de modelado

Para el analisis y el diseno del sistema se utiliza UML como lenguaje de modelado principal. UML permite representar de forma grafica y estructurada los actores, los casos de uso, las clases y las relaciones del sistema.

Dentro del proyecto, UML se aplica especialmente a:
- diagrama de clases para representar entidades y relaciones principales;
- modelado de casos de uso para describir interacciones entre actores y sistema;
- apoyo conceptual al diseno de subsistemas y separacion de responsabilidades.

Junto con UML, el modelo entidad-relacion se emplea para describir la base de datos relacional de la aplicacion.

4.4 Recursos hardware

Los recursos hardware necesarios para el desarrollo y demostracion de la parte web son modestos y propios de un entorno de desarrollo actual:
- equipo de desarrollo con procesador de proposito general;
- memoria suficiente para ejecutar servidor web local, base de datos y herramientas de desarrollo;
- almacenamiento local para codigo fuente, dependencias y base de datos;
- conexion de red para integraciones opcionales y pruebas de servicios externos.

Para el despliegue de la aplicacion web bastan los recursos habituales de un servidor capaz de ejecutar PHP, servir HTTP y mantener una base de datos relacional.

La infraestructura especifica del servidor de Counter-Strike constituye un recurso adicional y complementario. Puede enriquecer la demostracion funcional, pero no forma parte del nucleo evaluable del sistema web.

4.5 Recursos software

El software empleado en el proyecto es el siguiente:
- Laravel 12 como framework principal del backend.
- PHP 8.2 o superior como lenguaje y entorno de ejecucion del servidor.
- MySQL en despliegue y SQLite en desarrollo local para persistencia relacional.
- Blade como motor de plantillas para la capa de presentacion.
- JavaScript para la actualizacion dinamica de determinadas vistas.
- Tailwind CSS para el diseno visual de la interfaz.
- Laravel Broadcasting con Pusher como opcion de tiempo real.
- Polling como mecanismo alternativo cuando no existe proveedor realtime configurado.
- Composer y npm para gestion de dependencias.
- Vite como herramienta de apoyo al flujo frontend del proyecto.
- PHPUnit para pruebas.
- Git para control de versiones.
- Visual Studio Code como entorno de desarrollo.

La mayor parte del ecosistema utilizado es software libre o de uso ampliamente extendido en el desarrollo web actual, lo que favorece mantenibilidad, aprendizaje y reproducibilidad del trabajo.

4.6 Arquitectura

La arquitectura general del sistema responde a un modelo cliente-servidor dentro del ambito web.

Desde el punto de vista logico, la estructura se organiza asi:
- cliente web: navegador del usuario, encargado de mostrar la interfaz y ejecutar las interacciones en JavaScript;
- servidor de aplicaciones: aplicacion Laravel, donde residen rutas, controladores, logica de negocio, validaciones y servicios;
- base de datos: sistema relacional que almacena usuarios, servidores, lobbies, relaciones, configuraciones y resultados.

Sobre esta base, la aplicacion sigue ademas el patron MVC:
- Modelos: representan y gestionan las entidades persistentes del sistema.
- Vistas: construyen la interfaz mediante plantillas Blade.
- Controladores: coordinan peticiones HTTP, reglas de negocio y respuestas.

La arquitectura funcional puede dividirse en dos bloques:

Bloque principal evaluable
- autenticacion y sesion;
- gestion de usuarios y roles;
- vistas y navegacion;
- lobbies y estados;
- ranking, perfil, inventario y tienda;
- panel administrativo;
- persistencia y API JSON.

Bloque complementario de integracion
- autenticacion federada con Steam;
- recepcion de resultados mediante webhook;
- generacion de configuraciones para el sistema de partidos;
- envio de comandos RCON al servidor de juego.

Esta separacion es importante porque permite defender el proyecto como una aplicacion web completa e independiente. Las integraciones con Counter-Strike aumentan el valor practico del sistema, pero la arquitectura, la persistencia, la interfaz, los flujos y la logica funcional web siguen siendo el centro del desarrollo.

5. CONCLUSION

AfterReload se plantea como una aplicacion web completa para la gestion de una comunidad privada de juego, con una base funcional centrada en usuarios, lobbies, ranking, administracion y persistencia de datos. Su interes principal, a efectos de evaluacion, se encuentra en el desarrollo del sistema web y en la aplicacion de principios de analisis, diseno, implementacion y organizacion arquitectonica.

Las integraciones con el servidor de Counter-Strike deben presentarse como una capa adicional de especializacion. Son utiles para demostrar aplicacion practica y posibilidades de evolucion, pero no deben eclipsar la parte principal del trabajo, que es la construccion de un sistema de informacion web coherente, mantenible y funcional.
