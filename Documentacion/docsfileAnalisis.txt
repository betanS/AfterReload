5. ANALISIS

5.1 Identificacion de requisitos del software

Requisitos funcionales (RF)
RF1. El sistema debe permitir el inicio de sesion mediante Steam OpenID y crear o actualizar automaticamente el perfil local del usuario con su identificador, nombre visible y avatar.

RF2. El sistema debe mostrar un listado de servidores disponibles indicando nombre, tipo, estado de conectividad y ocupacion actual.

RF3. El sistema debe permitir el acceso a lobbies asociados a un servidor, incorporando automaticamente al usuario al lobby activo cuando exista capacidad y el acceso este permitido.

RF4. El sistema debe diferenciar entre servidores publicos y servidores de matchmaking. En los servidores publicos el usuario solo necesita conocer la direccion de conexion; en los servidores de matchmaking debe intervenir en un flujo de organizacion previa.

RF5. En lobbies de matchmaking el sistema debe permitir la seleccion de equipo CT o T, controlando el aforo por bando y evitando cambios cuando la partida ya este bloqueada.

RF6. En lobbies de matchmaking el sistema debe permitir marcar el estado de listo/no listo para cada jugador participante.

RF7. El sistema debe iniciar automaticamente la preparacion de la partida cuando se cumplan las condiciones de acceso al matchmaking: jugadores presentes, jugadores marcados como listos, equipos balanceados y configuracion tecnica disponible.

RF8. El sistema debe generar la configuracion JSON del encuentro para `get5`, almacenarla y servirla mediante un endpoint autenticado.

RF9. El sistema debe enviar comandos RCON al servidor de juego para configurar la integracion web, cargar el match y aplicar ajustes temporales durante la partida.

RF10. El sistema debe recibir eventos externos de `get5`, registrarlos, evitar procesados duplicados y cerrar el ciclo del match al finalizar la serie.

RF11. El sistema debe recalcular y persistir la puntuacion de ranking de los usuarios tras los resultados competitivos procesados.

RF12. El sistema debe ofrecer una vista de ranking global ordenada por puntos para consulta de los usuarios autenticados.

RF13. El sistema debe ofrecer un perfil de usuario con informacion de identidad Steam, rol, puntos de ranking y creditos internos.

RF14. El sistema debe incorporar un panel de administracion para consultar usuarios, cambiar roles y bloquear o desbloquear cuentas.

RF15. El sistema debe restringir el acceso a la tienda segun rol y permitir consultar un catalogo filtrable de skins con busqueda y paginacion sobre un repositorio local cacheado.

RF16. El sistema debe expulsar automaticamente del lobby a usuarios inactivos cuando dejen de enviar latidos de presencia durante el tiempo establecido.

RF17. El sistema debe impedir que un usuario bloqueado navegue por el sistema con normalidad y redirigirlo a una vista especifica de restriccion.

Requisitos no funcionales (RNF)
RNF1. Seguridad. Las operaciones protegidas deben ejecutarse bajo autenticacion; la API externa debe validarse mediante token y las credenciales sensibles deben residir en variables de entorno o configuracion del servidor.

RNF2. Integridad de datos. El sistema debe evitar duplicados en el registro de resultados mediante un hash unico por evento recibido.

RNF3. Disponibilidad operativa. La aplicacion web debe seguir funcionando aunque no haya proveedor realtime configurado, utilizando polling como mecanismo alternativo de actualizacion del lobby.

RNF4. Rendimiento percibido. Las vistas principales deben ofrecer respuesta inmediata en operaciones de consulta y refresco ligero, especialmente en listado de servidores y estado del lobby.

RNF5. Usabilidad. La navegacion debe ser simple para usuarios no tecnicos, con accesos visibles a servidores, ranking, perfil, inventario, tienda y administracion segun permisos.

RNF6. Mantenibilidad. La solucion debe apoyarse en una separacion clara entre rutas, controladores, modelos, servicios y vistas Blade, facilitando evolucion y depuracion.

RNF7. Escalabilidad funcional. Las integraciones con `get5`, RCON, broadcaster y catalogo de skins deben tratarse como modulos acoplados al nucleo web pero sustituibles o ampliables.

RNF8. Compatibilidad. La interfaz debe ser usable en escritorio y movil, manteniendo una estructura responsive en las pantallas principales.

5.2 Identificacion de actores del sistema

Visitante
- Puede acceder a la portada y comenzar el flujo de autenticacion con Steam.

Jugador autenticado
- Consulta servidores, ranking, perfil, inventario y, cuando el servidor lo permite, entra en lobbies.

Beta tester
- Es un jugador autenticado con permiso adicional para acceder al servidor de matchmaking.

Administrador
- Gestiona usuarios, roles y bloqueos desde el panel de administracion.

Servicio de autenticacion Steam
- Proveedor externo que valida la identidad del usuario y devuelve sus datos basicos de perfil.

Servidor de juego / plugin `get5`
- Consume la configuracion del match, envia eventos del encuentro y participa en la coordinacion tecnica de la partida.

Sistema RCON
- Canal tecnico utilizado por la aplicacion para enviar ordenes remotas al servidor de juego.

Fuente externa de skins
- Repositorio remoto del que se obtiene periodicamente el catalogo base de la tienda para su almacenamiento local.

5.3 Modelo del dominio

Entidades principales del dominio
- User: representa al usuario de la plataforma. Almacena identidad Steam, nombre, avatar, rol, estado de bloqueo, puntos de ranking y creditos.
- Server: representa un servidor disponible dentro de la plataforma. Almacena nombre, IP, puerto, tipo, aforo, ocupacion y credenciales RCON.
- Lobby: representa la sala activa asociada a un servidor. Controla el numero requerido de jugadores, el estado del ciclo de vida y la marca de inicio.
- LobbyUser: relacion de participacion entre usuario y lobby. Almacena el equipo seleccionado y el estado de listo.
- LobbyMatch: representa la configuracion tecnica del match generado para `get5`.
- MatchResult: representa cada evento o resultado recibido desde la integracion externa.

Relaciones del dominio
- Un Server puede tener muchos Lobby.
- Un Lobby pertenece a un Server.
- Un User puede participar en muchos Lobby.
- Un Lobby puede contener muchos User.
- La relacion Lobby-User incorpora los atributos `team` e `is_ready`.
- Un Lobby puede originar varios registros de LobbyMatch a lo largo de su ciclo historico, aunque solo uno puede estar activo para una partida en curso.
- Un Server puede estar asociado a varios MatchResult.

Diagrama Entidad-Relacion de la base de datos

Descripcion textual del E-R
- `users (id, steam_id, steam_nickname, steam_real_name, name, email, avatar, role, banned_at, rank_points, blue_credits, ...)`
- `servers (id, name, ip, port, rcon_password, type, max_players, current_players, ...)`
- `lobbies (id, server_id, name, required_players, status, started_at, ...)`
- `lobby_user (id, lobby_id, user_id, team, is_ready, ...)`
- `lobby_matches (id, lobby_id, server_id, match_id, config, status, created_at)`
- `match_results (id, event_hash, event_name, match_id, map_number, server_id, winner_team, team1_score, team2_score, payload, processed_at, ...)`

Cardinalidades
- `servers 1:N lobbies`
- `lobbies N:M users` mediante `lobby_user`
- `lobbies 1:N lobby_matches`
- `servers 1:N lobby_matches`
- `servers 1:N match_results`

Diagrama UML de clases

Clases de dominio y soporte directo
- User
  Atributos: steam_id, steam_nickname, steam_real_name, name, avatar, role, banned_at, rank_points, blue_credits
  Relaciones: N:M con Lobby

- Server
  Atributos: name, ip, port, rcon_password, type, max_players, current_players
  Relaciones: 1:N con Lobby

- Lobby
  Atributos: server_id, name, required_players, status, started_at
  Relaciones: N:1 con Server, N:M con User

- LobbyMatch
  Atributos: lobby_id, server_id, match_id, config, status, created_at
  Relaciones: N:1 con Lobby, N:1 con Server

- MatchResult
  Atributos: event_hash, event_name, match_id, map_number, server_id, winner_team, team1_score, team2_score, payload, processed_at
  Relaciones: asociacion logica con Server y con el match procesado

- LobbyController
- SteamController
- Get5Controller
- AdminController
- StoreController
- RconClient
- LobbyHeartbeatCleaner
- LobbyUpdated

Relaciones relevantes entre clases
- Los controladores usan los modelos para orquestar la logica de negocio.
- `LobbyController` depende de `RconClient`, `LobbyHeartbeatCleaner` y `LobbyUpdated`.
- `Get5Controller` usa `Lobby`, `LobbyMatch`, `MatchResult`, `Server` y `User`.
- `SteamController` usa `User` y la integracion Socialite con Steam.

5.4 Subsistemas de analisis

Subsistema de autenticacion y sesion
- Gestiona el acceso mediante Steam OpenID, la creacion o actualizacion del usuario local y el cierre de sesion.

Subsistema de gestion de usuarios y permisos
- Controla roles (`user`, `store`, `admin`, `betatester`), bloqueo de cuentas y restricciones de acceso a modulos.

Subsistema de servidores y lobbies
- Muestra servidores, calcula ocupacion, crea o reutiliza lobbies, registra permanencia y expulsa usuarios inactivos.

Subsistema de matchmaking
- Permite seleccionar equipo, marcar estado de listo, validar equilibrio de bandos y cambiar el lobby a estado de partida activa.

Subsistema de comunicacion en tiempo real
- Difunde cambios del lobby mediante broadcasting y usa polling cuando no hay proveedor realtime disponible.

Subsistema de integracion de partida
- Genera la configuracion del encuentro para `get5`, la expone por API y coordina el arranque tecnico de la partida mediante RCON.

Subsistema de resultados y ranking
- Recibe eventos del partido, registra resultados, evita duplicados, asigna puntos y cierra la partida.

Subsistema de tienda
- Descarga o reutiliza un catalogo local de skins, aplica filtros y devuelve listados paginados para la interfaz.

Subsistema de administracion
- Ofrece consulta de usuarios y operaciones de cambio de rol, bloqueo y desbloqueo.

5.5 Especificacion de casos de uso

CU1. Iniciar sesion con Steam
- Actor principal: Visitante
- Objetivo: acceder al sistema con identidad Steam.
- Precondiciones: configuracion de Steam habilitada.
- Resultado esperado: usuario autenticado y perfil local creado o actualizado.

CU2. Consultar servidores disponibles
- Actor principal: Jugador autenticado
- Objetivo: conocer que servidores estan operativos y cual es su ocupacion.
- Precondiciones: usuario autenticado.
- Resultado esperado: listado de servidores con estado y accion de acceso.

CU3. Acceder a un lobby publico
- Actor principal: Jugador autenticado
- Objetivo: obtener la informacion de conexion a un servidor publico.
- Precondiciones: servidor online.
- Resultado esperado: visualizacion del lobby y comando de conexion.

CU4. Acceder a un lobby de matchmaking
- Actor principal: Beta tester
- Objetivo: incorporarse a la sala competitiva del servidor MM.
- Precondiciones: usuario autenticado con permiso beta tester o administrador; servidor online.
- Resultado esperado: usuario unido al lobby activo.

CU5. Seleccionar equipo en matchmaking
- Actor principal: Beta tester
- Objetivo: elegir bando CT o T.
- Precondiciones: usuario dentro del lobby; partida no bloqueada; equipo con plazas libres.
- Resultado esperado: pivot `lobby_user` actualizado con el equipo elegido.

CU6. Confirmar disponibilidad
- Actor principal: Beta tester
- Objetivo: marcarse como listo o no listo.
- Precondiciones: usuario dentro del lobby; partida no bloqueada.
- Resultado esperado: actualizacion del estado de listo y reevaluacion del arranque del match.

CU7. Iniciar partida competitiva
- Actor principal: Sistema
- Objetivo: configurar tecnicamente el encuentro cuando todos los requisitos se cumplen.
- Precondiciones: jugadores suficientes, todos listos, equipos balanceados, token API, URL base y RCON disponibles.
- Resultado esperado: lobby en estado `live`, configuracion `get5` creada y orden de carga enviada al servidor.

CU8. Procesar resultado de partida
- Actor principal: Servidor de juego / plugin `get5`
- Objetivo: informar del progreso o fin del match.
- Precondiciones: token valido y evento no duplicado.
- Resultado esperado: evento almacenado, puntos actualizados si procede y lobby cerrado al finalizar la serie.

CU9. Consultar ranking
- Actor principal: Jugador autenticado
- Objetivo: visualizar la clasificacion global.
- Precondiciones: usuario autenticado.
- Resultado esperado: listado ordenado de jugadores por `rank_points`.

CU10. Gestionar usuarios
- Actor principal: Administrador
- Objetivo: cambiar roles y bloquear o desbloquear cuentas.
- Precondiciones: usuario con rol `admin`.
- Resultado esperado: estado del usuario actualizado en base de datos.

CU11. Consultar tienda de skins
- Actor principal: Usuario con permiso de tienda
- Objetivo: buscar y filtrar skins.
- Precondiciones: rol con acceso a la tienda.
- Resultado esperado: listado paginado ajustado a filtros y texto de busqueda.

5.6 Descripcion de casos de uso

Descripcion detallada de CU4, CU5, CU6 y CU7: flujo de lobby competitivo

1. El beta tester accede al listado de servidores y selecciona el servidor de matchmaking.
2. El sistema valida permisos, comprueba que el servidor esta online y localiza o crea el lobby activo.
3. El usuario se incorpora al lobby si existe capacidad y la partida no esta bloqueada.
4. El sistema asigna automaticamente un equipo inicial si el usuario aun no tiene uno.
5. El usuario puede cambiar manualmente a CT o T mientras existan plazas y la partida no haya comenzado.
6. El usuario pulsa el boton de listo para confirmar su disponibilidad.
7. Cada cambio se publica a los demas clientes mediante broadcasting o, en su defecto, es visible por polling.
8. Cuando todos los jugadores presentes estan marcados como listos y los equipos son validos, el sistema crea el registro `LobbyMatch`.
9. El sistema actualiza el lobby a estado `live`, configura la API web de `get5`, ajusta parametros del servidor y envia el comando `get5_loadmatch_url`.
10. La interfaz reemplaza el estado de espera por los datos de conexion al match, incluyendo password cuando existe.

Descripcion detallada de CU8: procesamiento del cierre de partida

1. El plugin `get5` envia un evento HTTP al endpoint de la API.
2. El sistema valida el token recibido.
3. El sistema calcula un hash del payload y verifica si el evento ya fue procesado.
4. El evento se registra en `match_results`.
5. Si el evento representa fin de mapa o de serie, el sistema identifica ganador y perdedor.
6. En servidores de tipo `mm`, el sistema aplica variacion de puntos a los usuarios implicados.
7. El sistema vacia el lobby, marca el encuentro como completado y restablece el conteo de jugadores del servidor.
8. Si existe configuracion RCON, se restauran determinados comandos deshabilitados durante el match.

Descripcion resumida de CU10: administracion de usuarios

1. El administrador accede al panel.
2. El sistema muestra el listado completo de usuarios con rol y estado.
3. El administrador modifica el rol o ejecuta una accion de bloqueo/desbloqueo.
4. El sistema valida la operacion y persiste el cambio.
5. La interfaz muestra un mensaje de estado confirmando el resultado.

5.7 Definicion y prototipo de la interfaz de usuario

Estructura general de la interfaz
- La aplicacion utiliza un layout comun con barra lateral, topbar y area principal de contenido.
- La interfaz se apoya en vistas Blade renderizadas en servidor y JavaScript ligero para interacciones dinamicas.
- El diseno es responsive y adapta tablas a tarjetas en pantallas pequenas.

Pantallas principales
- Portada: presenta el proyecto y ofrece acceso al login con Steam.
- Servidores: lista los servidores, su tipo, su estado online/offline y la accion de acceso.
- Lobby: muestra jugadores, equipos, estado de listo, informacion de conexion y actualizacion en tiempo real.
- Ranking: tabla de clasificacion de usuarios por puntos.
- Perfil: muestra identidad del usuario, rol, puntos y creditos.
- Inventario: pantalla informativa preparada para una futura gestion de equipamiento.
- Tienda: vista con filtros por categoria y arma, busqueda, paginacion y modal de compra simulado.
- Administracion: dashboard con metricas basicas y tabla/listado de usuarios con acciones de rol y bloqueo.

Prototipo textual de navegacion
- Visitante -> Portada -> Login Steam
- Jugador autenticado -> Servidores -> Lobby publico o competitivo
- Jugador autenticado -> Ranking
- Jugador autenticado -> Perfil
- Usuario con permiso -> Tienda
- Administrador -> Panel de administracion

Prototipo textual de la pantalla de lobby competitivo
- Cabecera con nombre del servidor y numero de lobby.
- Zona central con dos columnas: CT y T.
- Cada jugador se muestra con avatar, nombre y puntos.
- Indicador visual de jugador listo.
- Botones de union a equipo.
- Panel lateral con boton de listo, estado del lobby y, cuando procede, comando de conexion al servidor.

Criterios de interfaz relevantes para el analisis
- Visibilidad inmediata del estado del lobby.
- Minimizacion de pasos para entrar en partida.
- Separacion clara entre acciones de jugador y datos tecnicos de conexion.
- Restriccion visual de funcionalidades segun rol y contexto.

5.8 Analisis de los usuarios

Perfil 1. Visitante
- Necesita entender rapidamente la finalidad de la plataforma y disponer de un acceso simple al inicio de sesion.
- Su interaccion principal se limita a la portada y al redireccionamiento a Steam.

Perfil 2. Jugador estandar
- Busca consultar servidores, unirse a partidas publicas, revisar su posicion en el ranking y acceder a su perfil.
- Valora una interfaz rapida, clara y con poca carga cognitiva.

Perfil 3. Beta tester competitivo
- Utiliza el flujo de matchmaking y necesita informacion de estado en tiempo casi real.
- Requiere saber con claridad en que equipo esta, quien falta por confirmar y cuando puede conectarse al match.

Perfil 4. Administrador
- Necesita visibilidad completa del censo de usuarios y herramientas de control inmediatas.
- Prioriza operaciones simples, seguras y auditables sobre una interfaz recargada.

Perfil 5. Usuario con acceso a tienda
- Necesita exploracion visual del catalogo y herramientas rapidas de filtrado.
- Tolera mejor un modulo parcialmente desacoplado del gameplay siempre que la busqueda sea comoda.

Conclusiones del analisis de usuarios
- El sistema debe priorizar simplicidad para el jugador general y control para el administrador.
- El flujo de matchmaking requiere feedback continuo y restricciones claras para evitar errores operativos.
- La plataforma combina perfiles de uso distintos, por lo que los permisos y la visibilidad contextual son una pieza central del analisis.
